| Q2 | How does it connect to Architecture Advisor? | **Separate app + URL hand-off.** Architecture Advisor's result page gets a "Pick a stack for this" link to `/advisor?style=<style-id>` (same style ids, see `SIBLING_PROJECT.md`). The style pre-fills an optional field and fires a few small rules (KB schema §7.5). Why: both apps stay simple and independently deployable; a URL is the cheapest link; the sibling is finished and only needs a one-line change later. Do it in v1 (it's small) but build the AA side last. |
| Q3 | Rank each part separately, rank whole-stack bundles, or both? | **Per-part ranking + a deterministic "stack assembly" step**, with well-known bundles (MERN, LAMP, ...) shown as info only. Why: per-part lists are explainable ("PostgreSQL ranked #1 for these reasons"); assembly then picks the best *compatible* combination by enumerating at most ~3,000 options (`SCORING_ENGINE.md` step 6). Ranking bundles directly would hide why a part was chosen and needs a curated bundle for every case. |
| Q4 | Which parts of the stack are in v1? | **Language, frontend (approach + framework), backend (type + framework), database (type + product), hosting (type + provider).** These are exactly the five choices in your brief and they depend on each other, so they must be solved together. **Later, in this order:** (1) ORM, because it follows directly from language + database and beginners ask about it; (2) authentication; (3) caching and queues (Redis/Valkey as an add-on, message brokers for event-driven styles); (4) mobile (React Native, Flutter, native), which is a different decision tree. |
| Q5 / Q10 | Which tools go into v1, and how many per part? | **6–11 per part, mainstream and actively maintained**, as listed in `KNOWLEDGE_BASE_SCHEMA.md` §3: languages TS/Node, Python, Java (incl. Kotlin), C#, Go, PHP; frontend plain HTML, Astro, React, Vue, Svelte, Angular, Next.js, Nuxt, SvelteKit (+ backend templates); backend Express, Fastify, NestJS, FastAPI, Django, Spring Boot, ASP.NET Core, Laravel, Gin (+ the frontend framework's server); databases PostgreSQL, MySQL, SQLite, MongoDB, Redis, Valkey, Neo4j; hosting GitHub Pages, Netlify, Vercel, Cloudflare, Render, Railway, Fly.io, AWS, Azure, Google Cloud, a VPS. Why: covers the large majority of what the Stack Overflow 2026 survey shows people use, every language in your brief has at least one framework, and each part stays small enough to source properly. **Left for later:** Ruby/Rails, Kotlin-specific frameworks (Ktor), Flask, Hono, Remix/React Router, SolidJS, htmx, MariaDB, SQL Server (Q17), Cassandra. They go in the glossary so mentions still get an answer. |
| Q6 | Which criteria? | **The 16 in `KNOWLEDGE_BASE_SCHEMA.md` §4**: your list (learning curve, performance, scalability, ecosystem, community & hiring, maturity & long-term support, hosting cost, type safety, real-time) plus fast-to-build, SEO/first load, interactivity, data integrity, flexible data structure, low operations work, easy to move away. Each criterion applies only to the parts where it means something (type safety isn't a hosting question). Why: a stack-specific list is clearer than reusing architecture quality attributes; the extra ones are the trade-offs that actually separate options within a part (e.g. data integrity vs flexible structure for databases, from `ddia` ch.2). The form shows ~10 by default and the rest under "More priorities". |
| Q7 | How often is the KB refreshed, and what happens to old entries? | **Stale windows per fact kind** (free tiers 90 days, versions and support 180, licences 365, score evidence 365), a "checked on" date in the UI, a warning when overdue and a release-build failure at 2× overdue (`KNOWLEDGE_BASE_SCHEMA.md` §9). **A refresh session every 3 months.** Abandoned tools are marked `deprecated` and move to the glossary. Why: one 12-month window is too slow for free-tier limits (e.g. Render, Netlify and Fly.io all changed their free tiers in 2024–2026) and too fast for licences. |
| Q8 | Same tech stack as Architecture Advisor for the app itself? | **Yes:** Next.js (16.x now) + TypeScript strict + Zod + Tailwind/shadcn + Vitest/fast-check, Vercel Hobby, Gemini Flash-Lite → Groq → rules-only. Why: proven, free, and the engine/AI/KB modules can be adapted instead of rewritten. Vercel Hobby is non-commercial, which is fine as long as the app stays non-commercial (same as sibling Q9). Re-check AI model IDs and free limits in Phase 4 (they change often). |
| Q9 | Repo visibility | **Stay private** while `references/books/` holds the four PDFs. Publishing copyrighted book PDFs in a public repo would be redistribution. Note: the PDFs are now in the **git history**, so making this repo public later would need a history rewrite or a fresh public repo without them. If you want a public portfolio repo later, I recommend a fresh public repo at launch, with `references/` holding only `INDEX.md`. |
| Q11 | How should team skills be asked, and should there be a "learn something new" option? | **Per language: none / some / strong**, plus an optional "frameworks we know" multi-select, plus a goal toggle **"Use what we know" (default) / "Learn something new"** that halves the skill bonus. Why: skill is the strongest real-world factor in your brief; three levels are quick to answer; students often *want* to learn a new tool, and then a big Java bonus would be unhelpful. Proposed numbers: strong +20 to the language and +10 to its frameworks, capped at +25 per option (KB schema §7.4), tuned on the golden scenarios. |
| Q12 | Can the user lock a part ("we must use MongoDB")? | **Yes, in v1.** The locked option is always in the stack and the rest is assembled around it; if the lock clashes with a rule (e.g. Vercel + commercial + free only) we keep it and show a warning. Why: very common in real projects, cheap to support in stack assembly. |
| Q13 | Backend-as-a-service (Supabase, Firebase, Appwrite) in v1? | **Not ranked in v1; glossary cards instead,** ranked in v1.1 as a backend type. Why: they replace backend *and* database *and* auth at once, which breaks the clean part model; doing them well needs their free-tier and lock-in facts sourced (Supabase pauses free projects after 7 days idle, RESEARCH §4). They're popular for MVPs, so they deserve a proper design, not a rush. |
| Q14 | CMSs (WordPress), no-code tools and Python dashboard tools (Streamlit, Dash)? | **Out of scope for ranking; glossary cards that say when they're the better answer** (e.g. "for a content site your client edits, a CMS like WordPress may beat custom code"; "for an internal Python dashboard, Streamlit may be enough"). Why: being honest about "you may not need a framework" is part of being fair, but ranking them needs a different form. Affects golden G4 and G7. |
| Q15 | Ask "Is this a commercial project?" on the form? | **Yes.** Why: it changes facts, not preferences: Vercel Hobby is for non-commercial use only (RESEARCH §4), and some free tiers may have similar terms. Without the question we'd recommend something the user may not be allowed to use. |
| Q16 | How to treat licences? | **Show each product's licence with an "OSI open source: yes/no" badge, and an optional constraint "open-source licences only"** that excludes non-OSI products (rule K6). Why: MongoDB Community uses SSPL (not OSI-approved); Redis 8+ offers AGPLv3 alongside two source-available licences; Valkey is BSD (all checked from the repos, RESEARCH §2). Many companies and courses care; others don't, so it's a constraint, not a penalty. |
| Q17 | Commercial databases with free editions (SQL Server, Oracle)? | **Not in v1; glossary cards.** Why: their free editions have size limits and their main value is in companies already using them, which the "lock a part" feature covers. Add SQL Server in v1.1 if the C#/Azure scenario (G6) shows it's missed. |
| Q18 | Database hosting (Supabase, Neon, MongoDB Atlas, RDS)? | **v1: shown as notes under the database pick** ("managed options with free tiers: …", dated), **not ranked.** Rank in v1.1 as part of hosting. Why: keeps v1 to five parts; the free-tier facts need primary-source checks first (Q21). |
| Q19 | Mobile apps in v1? | **No.** "Backend for a mobile app" is an app kind in v1 (the backend, database and hosting still apply); the mobile framework itself (React Native, Flutter, native) is a later part. |
